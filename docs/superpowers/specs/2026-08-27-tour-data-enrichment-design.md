# 도착 마감 추천을 위한 TourAPI 데이터 보강 설계

작성일: `2026-08-27`

상태: 사용자 방향 승인, 구현 계획 작성 전

연결 설계: `docs/superpowers/specs/2026-08-26-deadline-aware-route-flow-design.md`

## 1. 목적

도착 마감 추천은 장소까지의 이동시간뿐 아니라 예상 도착 뒤 실제로 방문 가능한지도
판단해야 한다. 현재 운영 DB에는 강원특별자치도 장소 783곳이 있지만 공개 API에서
운영시간이 확인되는 장소는 9곳뿐이다. 새 추천 모델을 출시하기 전에 다음 데이터 기반을
만든다.

- 운영시간과 휴무일을 우선 보강해 최대 체류시간의 영업 종료 상한을 계산한다.
- TourAPI 소분류를 보존해 음식점과 카페를 구분한다.
- 축제 기간이 지난 장소를 활성 추천에서 제외한다.
- 변경·삭제된 관광 콘텐츠를 전체 재수집 없이 증분 반영한다.
- 장소 소개와 홈페이지를 상세 화면에 제공하되 시간 계산 데이터보다 낮은 우선순위로 수집한다.

별도 활용신청이 필요한 관광 소요시간·연관 관광지 API는 이번 구현 범위에 넣지 않는다.
향후 소프트 랭킹 데이터로 연결할 수 있는 경계만 유지한다.

## 2. 현재 구조에서 확인된 문제

현재 기본 동기화는 `areaBasedList2`의 원본 응답을 `places.raw`에 저장한다. 상세 동기화는
`detailIntro2`, `detailImage2`, `detailPetTour2` 결과를 같은 `places.raw._tteumsae`에 합친다.
다음 기본 동기화가 같은 행을 upsert하면 새 기본 원본으로 `raw` 전체가 다시 저장되므로,
이전에 합친 상세 데이터가 사라질 수 있다.

또한 상세 동기화는 하루 10곳을 처리하면서 장소마다 세 API를 함께 호출한다. 이 구조에서는
운영시간 한 필드가 필요한 장소도 이미지·반려동물 호출이 끝나야 같은 속도로 전진한다.
시간 계산에 필요한 데이터와 상세 화면용 데이터를 같은 작업으로 묶은 것이 병목이다.

## 3. 검토한 접근

### 3.1 기존 `raw._tteumsae` 병합 유지

마이그레이션이 작지만 기본 upsert와 상세 갱신의 소유권이 계속 충돌하고, 운영시간으로 DB
필터를 만들기 어렵다. 현재 문제를 그대로 남기므로 제외한다.

### 3.2 `places` 정규화 컬럼과 별도 `enrichment_raw` 사용 — 선택

목록·추천이 자주 쓰는 필드는 정규화 컬럼으로 두고 상세 원본은 기본 원본과 다른 JSON 컬럼에
둔다. 현재 PostgREST 조회 구조를 크게 바꾸지 않으면서 덮어쓰기를 막고, 필터와 운영 점검도
단순해진다.

### 3.3 별도 `place_details`와 작업 큐 테이블 도입

대규모 다국어·다중 공급자 확장에는 가장 명확하지만 현재 783곳과 단일 국문 공급자 규모에는
조인, RLS, 배포 순서가 과하다. 별도 활용신청 데이터 공급자를 실제 도입할 때 다시 검토한다.

## 4. 확정 원칙

1. 기본 원본과 상세 보강 원본을 서로 다른 저장 경계로 분리한다.
2. 추천 정확도에 필요한 `detailIntro2`를 가장 먼저 전체 백필한다.
3. TourAPI 호출은 사용자 추천 요청 중에 실행하지 않고 서버 동기화 작업에서만 실행한다.
4. 영업시간을 알 수 없다는 이유만으로 장소를 제외하지 않는다. `영업시간 확인 필요` 상태를 유지한다.
5. 평균 체류시간이나 연관 방문 통계는 향후에도 가능 여부의 하드 조건으로 사용하지 않는다.
6. 후보 가능 여부는 도착 마감, 정확 경로 이동시간, 안전 여유 10분, 최소 체류 15분으로만 판정한다.
7. TourAPI 실패는 기존 DB 데이터를 지우지 않는다. 마지막 성공 데이터를 유지하고 재시도한다.
8. 개발계정 호출량과 Vercel 실행시간을 넘지 않도록 각 작업의 배치 크기와 동시성을 제한한다.

## 5. API 선택

### 5.1 이번 구현에 사용

| API | 역할 | 우선순위 |
|---|---|---|
| `areaBasedList2` | 초기 강원 장소 목록과 `cat1/cat2/cat3` 수집 | 기존 유지 |
| `detailIntro2` | 운영시간, 휴무일, 주차, 행사 기간 등 유형별 방문 정보 | 최우선 |
| `areaBasedSyncList2` | 수정 시각 이후 변경된 장소와 표출 상태 증분 반영 | 높음 |
| `detailCommon2` | 장소 소개와 홈페이지 | 중간 |
| `searchFestival2` | 현재·예정 축제 기간 보정과 종료 축제 판정 | 중간 |
| `detailImage2` | 상세 화면 이미지 목록 | 기존 유지, 후순위 |
| `detailPetTour2` | 반려동물 동반 정보 | 기존 유지, 후순위 |

`areaBasedSyncList2`의 표출 상태 값은 실제 응답 fixture로 추가·수정·비표출 사례를 고정한 뒤
활성화한다. 문서에 없는 값이나 빈 응답을 삭제로 추정하지 않는다.
현재 명세에서 `areaCode`는 법정동 코드로 대체 예정이므로 강원 증분 조회는 기존
`areaCode=32`와 강원특별자치도 법정동 시도코드 `lDongRegnCd=51`을 함께 보낸다.

### 5.2 보류

| API | 보류 이유 |
|---|---|
| `detailInfo2` | 메뉴·프로그램·코스 정보는 유용하지만 도착 마감 계산에는 필요하지 않다. 핵심 백필 후 추가한다. |
| `locationBasedList2` | 현재 DB 좌표 필터와 Kakao 정확 경로 계산이 담당한다. 요청 시 TourAPI 호출은 지연과 쿼터를 늘린다. |
| `searchKeyword2` | 앱의 출발지·목적지 검색은 Kakao 검색을 유지한다. |
| `searchStay2` | 숙박은 짧은 경유지 제품 범위가 아니다. |
| 지역·법정동·분류 코드 API | 현재 강원 고정 코드와 응답의 분류 코드를 저장할 수 있어 런타임 호출이 필요 없다. |

### 5.3 향후 별도 데이터 소스

- 관광지별 관광 소요시간 집계: `typicalStayMinutes` 같은 소프트 랭킹 신호로만 사용한다.
- 관광지별 연관 관광지 정보: 두 번째 경유지 탐색의 정렬 신호로만 사용한다.
- 두 데이터가 없거나 오래돼도 추천 가능 여부와 정확 경로 검증은 동일하게 동작한다.
- 외부 식별자를 `content_id`로 간주하지 않고 별도 매핑 테이블에서 이름·좌표·주소 기반 매칭과
  신뢰도를 관리한다.

## 6. 데이터 구조

### 6.1 `places` 정규화 컬럼

기존 `places.raw`는 `areaBasedList2` 기본 원본만 보존한다. 다음 컬럼을 추가한다.

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `cat1`, `cat2`, `cat3` | `text null` | TourAPI 서비스 분류 원본 |
| `opening_hours` | `text null` | HTML 제거 후 운영시간 원문 |
| `closed_days` | `text null` | HTML 제거 후 휴무일 원문 |
| `event_start_date`, `event_end_date` | `date null` | 축제·행사 유효 기간 |
| `overview` | `text null` | HTML 제거 후 장소 소개 |
| `homepage_url` | `text null` | 허용 스킴으로 정규화한 공식 홈페이지 |
| `image_urls` | `jsonb not null default '[]'` | 중복 제거한 상세 이미지 URL |
| `tags` | `text[] not null default '{}'` | 주차·아이·반려동물·실내 등 파생 태그 |
| `enrichment_raw` | `jsonb not null default '{}'` | 상세 API별 원본과 출처 메타데이터 |
| `intro_synced_at` | `timestamptz null` | 시간 중요 상세의 마지막 성공 시각 |
| `common_synced_at` | `timestamptz null` | 공통 상세의 마지막 성공 시각 |
| `media_synced_at` | `timestamptz null` | 이미지·반려동물 상세의 마지막 성공 시각 |
| `enrichment_attempts` | `integer not null default 0` | 연속 실패 횟수 |
| `enrichment_last_error` | `text null` | 운영 확인용 축약 오류 |
| `next_enrichment_at` | `timestamptz null` | 지수 백오프 이후 재시도 시각 |

기본 목록 upsert는 상세 컬럼과 `enrichment_raw`를 보내지 않는다. 따라서 기본 목록 갱신이
상세 보강 결과를 덮어쓰지 않는다. 공개 장소 응답은 더 이상 `raw._tteumsae`를 읽지 않고
정규화 컬럼을 읽는다.

### 6.2 카페 분류

`content_type_id=39` 전체를 음식점으로 고정하지 않는다. `cat3` 분류 코드 테이블에서 카페·찻집
분류로 확인된 코드만 `CAFE`, 나머지는 `RESTAURANT`로 매핑한다. 코드 목록은
`categoryCode2`의 공식 응답 fixture와 테스트에 고정하며 장소명에 `카페`가 있다는 이유만으로
분류하지 않는다. 분류 코드가 없거나 알 수 없으면 기존 `RESTAURANT` fallback을 사용한다.

## 7. 동기화 작업 분리

### 7.1 카탈로그 작업

1. 초기 또는 복구 시 `areaBasedList2` 전체 순회를 사용한다.
2. 정상 운영에서는 마지막 성공 수정 시각을 기준으로 `areaBasedSyncList2`를 호출한다.
3. 추가·수정 항목은 기본 컬럼만 upsert하고 해당 장소의 필요한 상세 단계만 다시 대기시킨다.
4. 비표출 항목은 공식 표출 상태 의미가 fixture로 검증된 경우에만 `is_active=false`로 바꾼다.
5. 페이지 중간 실패 시 성공한 마지막 페이지와 수정 시각을 분리해 저장해 중복 실행에 안전하게 한다.

### 7.2 시간 중요 상세 작업

`intro_synced_at is null`이거나 원본 수정 시각보다 오래된 활성 장소를 우선 선택한다.
각 장소에 `detailIntro2` 한 번만 호출해 운영시간, 휴무일, 행사 기간, 주차·유아 관련 필드를
정규화한다. 제한된 동시성으로 처리하고 Vercel 종료 여유를 남기고 다음 커서를 저장한다.

이 작업이 전체 장소를 한 번 통과하기 전에는 소개·이미지 작업이 같은 장소를 선점하지 않는다.
새 추천 플로우 출시 전 운영시간 보강률과 실패율을 운영 점검에 표시한다.

### 7.3 표현 상세 작업

시간 중요 상세가 성공한 장소를 대상으로 `detailCommon2`, `detailImage2`, `detailPetTour2`를
각각 독립 결과로 저장한다. 한 API 실패가 다른 성공 결과를 버리지 않으며, 성공한 단계는
다음 실행에서 다시 호출하지 않는다. `detailInfo2`는 현재 호출하지 않지만 동일한 단계형 계약으로
나중에 추가할 수 있다.

### 7.4 축제 작업

`searchFestival2`로 오늘 이후의 강원 행사 목록을 동기화해 시작일과 종료일을 갱신한다.
추천 쿼리는 `FESTIVAL`에 한해 종료일이 오늘보다 이전인 장소를 제외한다. 날짜 정보가 없는
일반 관광지는 기존 동작을 유지하고, 빈 축제 응답만으로 장소를 삭제하지 않는다.

## 8. 추천 서비스 연결

- `minutesUntilClosing`은 DB의 `opening_hours`, `closed_days`를 사용한다.
- 구조적으로 해석한 닫는 시각이 이동 예산보다 빠르면 `maximumStayMinutes`를 그 시각까지 줄인다.
- 운영시간이 없거나 해석 불가능하면 이동 예산으로 추천하되 `operationStatus=UNKNOWN`을 반환한다.
- 종료된 축제는 후보 조회 단계에서 제외해 Kakao 경로 호출을 낭비하지 않는다.
- `cat3` 기반 `CAFE` 분류는 기존 사용자 관심 조건에 즉시 반영한다.
- `overview`, `homepage_url`, 이미지, 태그는 상세 화면에만 사용하고 시간 계산에 관여하지 않는다.

## 9. 오류 처리와 운영 관측

- TourAPI HTTP 실패, 비정상 `resultCode`, 데이터 없음은 서로 구분해 기록한다.
- 데이터 없음은 성공한 빈 상세로 저장할 수 있지만 기존 정상 값을 즉시 지우지 않는다.
- 실패는 연속 횟수에 따라 재시도 시각을 늦추고 다른 장소의 진행을 막지 않는다.
- Cron 응답은 단계, 처리 수, 성공 수, 실패 수, 남은 미보강 수, 다음 커서를 반환한다.
- `/api/health` 또는 운영 전용 점검 응답에서 총 장소 수, 운영시간 보강 수, 오래된 상세 수,
  마지막 카탈로그·인트로·표현·축제 성공 시각을 확인할 수 있게 한다.
- API 키와 원본 오류 본문 전체는 DB·응답·로그에 남기지 않는다.

## 10. 테스트 전략

### 10.1 마이그레이션과 저장

- 기본 목록 upsert 후에도 기존 상세 컬럼과 `enrichment_raw`가 유지된다.
- 공개 응답은 `raw._tteumsae` 없이 정규화 컬럼을 반환한다.
- 서비스 역할만 상세·동기화 상태를 쓸 수 있고 익명·인증 사용자는 직접 접근할 수 없다.

### 10.2 TourAPI fixture

- `cat3` 카페/음식점/미확인 분류
- 유형별 `detailIntro2` 운영시간·휴무일·행사 기간 정규화
- `detailCommon2` 소개 HTML 제거와 홈페이지 URL 검증
- 단일 객체, 배열, 빈 items 응답
- `areaBasedSyncList2` 추가·수정·비표출과 수정 시각 커서
- `searchFestival2` 진행 중·예정·종료 경계

### 10.3 작업 복원력

- 한 상세 API 실패 시 다른 단계의 성공 결과 유지
- 재실행 시 완료 단계 호출 생략
- 배치 중간 실패 후 마지막 성공 커서부터 재개
- 반복 실행과 중복 응답의 멱등성
- 호출량·동시성 상한과 재시도 백오프

### 10.4 추천 회귀

- 운영 종료 14분 전 제외, 15분 전 포함
- 운영시간 미확인 장소는 경고와 함께 이동 기준 추천 유지
- 종료된 축제 제외
- 카페 관심 조건이 `cat3` 기반 카페만 선택
- 기존 `extraTimeMinutes` 요청과 `/api/route` 계약 유지

## 11. 배포 순서

1. 상세 컬럼 마이그레이션과 기존 `raw._tteumsae` 데이터 이전을 적용한다.
2. 기본 upsert가 상세 데이터를 지우지 않는지 운영 스모크 테스트한다.
3. `detailIntro2` 전용 작업을 배포하고 전체 백필을 진행한다.
4. 운영시간 보강률과 실패율을 확인한 뒤 도착 마감 추천 계산을 활성화한다.
5. `areaBasedSyncList2` 증분 작업과 카페 재분류를 활성화한다.
6. `detailCommon2`, 이미지, 반려동물 표현 상세를 단계적으로 백필한다.
7. `searchFestival2` 날짜 필터를 활성화한다.
8. 별도 활용신청 API는 실제 매핑률과 데이터 최신성을 별도 spike로 검증한 뒤 결정한다.

## 12. 비목표

- 추천 요청 중 TourAPI 실시간 호출
- 평균 체류시간을 사용한 방문 가능/불가능 판정
- 연관 관광지 통계를 정확 경로 계산 대신 사용
- 숙박 장소 추천
- 데이터가 없다는 이유로 전체 장소를 일괄 비활성화
- 이번 단계의 무장애·날씨·혼잡도 개인화

## 13. 완료 기준

- 매일 기본 목록 동기화 후에도 상세 보강 데이터가 보존된다.
- 모든 활성 장소가 시간 중요 상세의 성공 또는 명시적 데이터 없음 상태를 갖는다.
- 운영시간·휴무일·행사 기간이 도착 마감 추천에 안전하게 반영된다.
- 카페와 일반 음식점이 공식 소분류에 따라 구분된다.
- 수정·비표출 장소를 전체 재수집 없이 증분 반영할 수 있다.
- 상세 화면이 소개·홈페이지·이미지·태그를 단계적으로 표시한다.
- TourAPI 장애나 쿼터 초과가 기존 추천과 저장 데이터를 삭제하지 않는다.
- 신규 동기화·마이그레이션·추천 테스트와 기존 백엔드 회귀 테스트가 통과한다.
